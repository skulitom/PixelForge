# Tidewatch findings log (running)

Raw notes kept while building the showcase. The final, verified write-up is `docs/reports/tidewatch-showcase-report.md`. Status: **suspected** (from source reading, not yet reproduced), **confirmed** (reproduced), **friction** (works, but costly), **missing** (feature gap).

## From reading the source before starting

- S1 (suspected bug) `src/mcp.js`: an MCP line over 2 MiB throws inside the read loop, which rejects `startMCP` and ends the process, instead of answering with a JSON-RPC error.
- S2 (missing) MCP exposes only sprite-recipe tools. Pose compilation, scenes, overlays, tile review and PNG import are CLI/JS only, so an MCP-only agent cannot review a scene.
- S3 (missing) No shared palette or include mechanism between recipes; a multi-recipe game must copy the palette into every file.
- S4 (missing) Every frame in a recipe has the same canvas size, and atlases are always untrimmed. A character whose attack reaches farther than its walk pays for the largest pose in every frame.
- S5 (suspected design bug) `inspectTile` reports rows/columns where the first and last pixel differ. Seamless tiles do not need identical opposite edges; identical edges produce a doubled seam column. The check flags good tiles and passes some bad ones.
- S6 (friction) Scene manifests must inline whole recipes; there is no file reference, so scenes need a build step.
- S7 (missing) The runtime `SpritePlayer` owns one canvas per sprite. There is no helper for drawing atlas frames into a shared game canvas with timing lookup.

## During the build
- F1 (confirmed limit) Scene manifests allow only 256 placement declarations. A single 240×160 screen of 16×16 tiles needs 150 placements per layer, so an autotiled map with water + sand + grass (≈310) cannot be reviewed as a scene. `repeat` only covers uniform rectangles; there is no tilemap construct (grid of frame names). Workaround: one repeated water instance, losing variants.
- F2 (friction) Clipping warnings are a single deduplicated string, "Some drawing falls outside the canvas and is clipped.", with no frame, operation path or pixel count. A 1px overhang in one of 12 water frames took manual arithmetic to find.
- F3 (missing) No way to copy a sub-rectangle of a symbol or earlier frame. Standard autotile templates (draw one small island + inner corners, slice into 8×8 quarters) cannot be expressed; I pre-split the template into 20 quarter symbols with a script.
- F4 (friction) Palette cycling (foam, water) must be emulated with per-frame `replace` ops and unique "marker" colors that never appear in the final art. Four phases × 47 tiles = 564 replace ops. A palette-animation construct or per-frame palette override would express this directly.
- F5 (confirms S5) `inspectTile` reported mismatched rows 9/14 on water tiles that repeat seamlessly (a dark stroke touching one edge is not a seam). The helper is also not reachable from the CLI or MCP.
- F6 (missing) `translate` clips; there is no wrap-around shift for scrolling tile animations (water, conveyor, clouds). Emulating it means drawing each stamp twice and accepting clipping warnings.
- F7 (missing) No outline/stroke operation for a layer, symbol or shape. Foliage clusters need a single silhouette outline around their union; I emulated it by deriving 1px-dilated copies of each cluster symbol and stamping them in a layer underneath. A `layer.outline` color (or an `outline` op) would remove that.
- F8 (limit) Scene lighting only changes assets that provide a normal or emissive pass (`renderScene` skips the lighting math otherwise). A night preview therefore leaves every plain asset at full daylight brightness; there is no global ambient darkening or "flat normal" default.
- F9 (missing) Plain recipes cannot declare a pivot/anchor (per recipe or per frame), and the atlas has no pivot field. Only pose sources carry origins. Every prop in the game needed a hand-measured anchor table (lighthouse ground line, trunk base, pot base...), duplicated outside PixelForge.
- F10 (missing) No per-frame custom metadata (glyph advance, hitbox, tags). The font's variable widths are measured from exported pixels at runtime; hitboxes live in game code. Pose markers only exist for compiled poses.
- F11 (friction) Frame/animation names must be unique ignoring case (for case-insensitive filesystems), so a font cannot name glyphs `A` and `a`; glyphs became `uA`/`la`/`n0`/`period` plus a separate character map file.
- F12 (friction) JS object key order puts integer-like keys first, so a scaffold that builds frames from `{A:…, 0:…}` silently reorders them. Not a PixelForge bug, but frame order in `frames[]` drives atlas layout; worth a note in the authoring guide for generator authors.
- F13 (suspected runtime issue) `SpritePlayer.load` awaits `image.decode()`. In the desktop app's hidden browser pane, `decode()` stayed pending until something forced a paint (a screenshot), so a page built the same way never started. Background tabs may behave similarly. Resolving on `onload`/`onerror` avoids it. Observed in Tidewatch's own loader; the exported `player.js` has the same pattern.
- F14 (confirms S1, bug) One MCP line over 2 MiB terminates the server (exit code 1, stderr `{"ok":false,"error":"MCP message exceeds 2 MiB"}`). The offending request gets no JSON-RPC reply and later requests fail with EOF. Reproduced with a 2.3 MB `pixel_validate` call. A per-message error (and continuing to read) would keep the session alive.
- F15 (limit mismatch) The recipe format allows 65,536 `pixels` corrections per frame, but one such frame serializes to ~2.3 MB, above the MCP 2 MiB line limit, so a schema-valid recipe cannot be sent over MCP at all (and, per F14, sending it kills the server).
- F16 (agent cost) `pixel_render` returns every exported file as an absolute path. For the 188-frame shore recipe the text content is 40,419 characters (~10K tokens) per render, almost all of it `frames/*.png` paths. A directory plus counts and the key files (atlas, sheet, playback) would cut this by >95%.
- MCP worked well otherwise: content-addressed revisions (same recipe → same id across processes), onion/diagnostics/grid-with-rulers inspection, exact error paths (`changes[0].value.rows[1]: unknown palette character "x"`), and a 5-pixel `grid` patch reported exactly those 5 pixels with `scope: "frame"`.
- F17 (confirmed) PNG import is genuinely lossless: the 40-frame keeper atlas and the lighthouse normal atlas round-trip with identical RGBA, durations and all 14 animations (64 ms). Pose structure (parts, markers) is not recoverable, as documented.
- F18 (cross-feature limit) A rich 256×256 import (>80 colours) becomes explicit `pixels`; wrapping that recipe in a `pixel_validate` call is a 2.43 MB MCP message, over the 2 MiB line limit (and per F14 fatal to the server). Imported editor art at the maximum canvas cannot enter the MCP workflow.
- F19 (friction, by design) Overlays on compiled poses survive an identical rebuild, but any source edit conflicts, including an unrelated `idle-0` duration change (900 → 950 ms) against a `snap-2` pixel correction. For pose sources under active iteration, corrections effectively have to be re-authored after every edit; a per-frame fingerprint would let unrelated frames keep their overlays.
- F20 (UX) Scene viewer: only `lighting.lights[0]` is movable (x/y sliders); other lights are fixed. `preview` warns "5537 drawn pixels clipped at scene bounds" without naming the placements.
- F21 (missing) No per-stamp palette remap. Flower colour variants, a hurt-flash white jelly or a blue crab need duplicated symbols/grids (I generated flower variants from a JS template). `stamp` with `remap: {"1": "4"}` would keep one authored shape.
- F22 (missing) Pose part instances cannot be mirrored. Left-facing keeper parts are programmatic mirrors of the right-facing ones (anchors/points flipped by hand in the scaffold); frame-level `flipX` exists for recipes but not in pose sources.
- F23 (evidence for S4) Untrimmed atlases: trimming each frame to its visible bounds would save 75% of the keeper atlas (64,000 → 16,226 px), 75% of slash arcs, 82% of effects, 46% of the crab.
- F24 (API ergonomics) `compilePoses` returns null-prototype maps (`symbols`, `metadata.poses`), so `assert.deepStrictEqual(compiled, JSON.parse(file))` fails until the result is JSON-normalised.
